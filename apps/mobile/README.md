# Hexbot mobile

An Expo React Native client for iOS and Android. The UI design was produced with
Claude Opus 5.5 from the supplied visual reference. iOS 26 uses native Liquid
Glass on floating controls; older iOS uses system blur. Android and Reduce
Transparency use solid controls. Lists and messages use solid backgrounds.

## Layout

Three tabs: Bots, Rooms and Daemon. Bots is a feed of bot posts. A bot opens
its one chat. Settings, bot settings, tool
steps and visuals open as front cards (`src/ui/Layer.tsx`) that leave the
screen below in view. The daemon name above Bots switches daemons. The model
pill lists the providers with a key or sign-in, plus the bot's own, each from
`hexbot.models.list {provider}` so the provider's current list is used, as in
the web app. Thinking levels come from `reasoning_levels`; a model the daemon
knows nothing about offers every level. The pill and the selected level show
the level the model runs at, which Pi rounds to one it supports.

## Run

From the repository root:

```sh
pnpm install --frozen-lockfile
pnpm mobile:ios       # Xcode, simulator or signed iPhone required
pnpm mobile:android   # Android SDK, JDK and emulator or device required
pnpm mobile:dev       # Metro; use an installed native app or Expo Go
```

`pnpm --filter @hexbot/mobile run web` opens the browser preview. Expo SDK 57,
React Native 0.86 and React 19 are pinned by the workspace lockfile. Native
projects are generated by Expo and gitignored.

On a physical phone, use the daemon computer's LAN or Tailscale address rather
than `localhost`. Enable local connections on the daemon and allow iOS local
network access. Get a code through Settings, Devices on a paired client or
`hexbot pair` on the daemon computer. Paste the address and code or a pairing
link. `hexbot://pair` opens the installed app with the address filled in. Check the
host shown above Pair and tap to confirm.

Hex Connect uses the system browser at `connect.hexbot.app`. Sign in, then
choose an online registered daemon. The app validates the callback state,
requests a grant bound to its device key, verifies the pinned daemon identity
when Connect supplies one, and exchanges the grant directly with that daemon.

## Controls

| Area | Mobile controls |
| --- | --- |
| Bots | Feed with role and description; create, edit, delete, soul, picture, model and thinking level, tools, approvals, workspace, notifications and dreaming |
| Conversations | Streamed chat, stop, file/image/PDF attachments, Markdown, tool steps with their results, visuals, questions and approvals |
| Rooms | Rooms in one tab: chat, stop, switch rooms, bot membership, main bot, budgets, approvals, archive, restore and delete |
| Memory | Edit each bot's memory and your About you text; inspect dreaming and restore memory |
| Models | Provider API keys and device sign-in, model selection, daemon defaults and fallback model |
| Jobs | Create, edit, pause, resume, run and delete; schedule, prompt, script, workspace, model, reasoning, skills and run count |
| Daemon | Settings, usage, bot activity, connectors and MCP servers, skill library, LAN pairing, Hex Connect and available daemon updates |
| Devices | List and revoke paired devices, switch or forget saved daemons |

One person owns the daemon and can choose Auto, Manual or Bypass approvals. Tool changes apply from the chat's next
message; soul changes after it next summarises older messages. Model and
thinking changes move the chat from its next message unless it has its own
override. Jobs use the daemon's
timezone and save their output there. Job details show the last status, error
and up to 12,000 characters of output. Push notifications and computer power
controls are outside this app's scope.

Credentials and the device proof key use Expo SecureStore. Connection names and
addresses use AsyncStorage. The browser preview holds credentials only in memory.
A revoked phone returns to pairing. Backgrounding closes the socket while the
daemon continues working; foregrounding restores history and pending dialogs
for active turns. Rooms keep each bot’s streaming text, tools and pending cards
separate. Failed turns and budget limits appear in the room history. A room
opens at its latest 200 events and pages back with `before_seq` on
`hexbot.rooms.log`; older daemons ignore it and the app reads the whole log.
A bot's chat takes one message at a time, so Stop replaces Send while it works.

Attachments stay on the phone until Send. Sending files without text uses
"Please review the attached files." Chips clear only after the daemon accepts
the message. Answer bot questions before sending attached files; the files stay
ready for the next message. Failed uploads can be retried without
resending attachments that already reached the daemon. Each upload returns an
id, and `prompt.submit` names the ids for that message: the daemon sends only
those and keeps other files staged. Leaving the chat, switching daemons or
disconnecting asks the daemon to clear unsent uploads; that clear is best effort.
This uses the new `attachments.clear` RPC and the `attachments` list on
`prompt.submit`; requests without this list send every staged file for compatibility. Scheduled job controls use the new
owner-scoped `hexbot.jobs.*` RPCs; use a daemon built from this checkout for both. The app shows an update notice
for older daemons and explains when either RPC is unavailable.

Bot visuals open in an isolated WebView or a sandboxed iframe, with the same CDN
and network restrictions as the browser client's visuals. Native visuals have
no app message bridge or shared cookies. Ordinary links in Markdown open in the
system browser. Visual links require confirmation on native platforms.

## Builds

`eas.json` contains development simulator, internal preview and production
profiles. Preview produces an Android APK and an iOS internal distribution build.
iPhone distribution requires Apple signing and registered devices. App Store
and Play Store releases require their respective accounts and credentials.
iOS beta builds are distributed through TestFlight.

```sh
cd apps/mobile
pnpm exec eas build --platform ios --profile preview
pnpm exec eas build --platform android --profile preview
```

Local native builds use
`pnpm mobile:ios` and `pnpm mobile:android` and need no EAS account.

Check-in notifications use push through the EAS project above
(`extra.eas.projectId` in `app.config.ts`), with APNs and FCM credentials on
it. On a daemon reached through Hex Connect, the daemon asks Connect to wake the phone; the push says only that
the primary bot has a message, never what it is.

## TestFlight automation

The EAS project is `@the1uneed/hexbot-mobile`; the installed app is Hexbot,
with bundle identifier `app.hexbot.mobile`. `eas.json` maps production
submissions to App Store Connect app `6824190699`. EAS stores the signing
certificate, provisioning profile and assigned App Store Connect API key.
Production build numbers are stored remotely and increment automatically.

The GitHub Release action starts `.eas/workflows/testflight.yml` in Expo
when its resolved channel is nightly and release checks pass. This includes
manual nightlies and scheduled nightlies with new commits. Stable releases
skip iOS. Ordinary pushes to `main` do not start a mobile release.
The workflow builds the exact release commit. It checks the mobile
app, builds iOS, then uploads that exact build through the standard EAS
Submit job. This works on the free Expo plan; the advanced `testflight` job
for uploading EAS builds requires a paid plan. A failed upload fails the
workflow; a successful build alone does not count as a successful upload.
Each stage and its logs appear in the project's Workflows page. Workflow
success means Apple accepted the upload. Apple processes the binary afterward.

One-time setup in the [Expo GitHub settings](https://expo.dev/accounts/the1uneed/projects/hexbot-mobile/github):

1. Install or authorize the Expo GitHub app for `The1UNeed/hexbot` and link
   that repository to this EAS project.
2. Set the app's base directory to `apps/mobile`. Commit and merge the
   workflow files and app configuration into `main` so Expo can read them.
   Add an Expo access token as the GitHub repository secret `EXPO_TOKEN` so
   the Release action can start and monitor the workflow. Nightly preflight
   fails clearly when this secret is missing; stable does not require it.
3. In App Store Connect, enable automatic distribution on the internal
   TestFlight group that should receive new builds and add the testers once.
   The workflow does not automatically submit external Beta App Reviews.

Subscribe to EAS Build and EAS Submit result emails in the Expo project's
Notifications settings to receive success and failure notices.

The stored Apple credentials must be valid and the assigned API key must
have upload access to this app. Apple credentials stay in Expo; GitHub uses
only the Expo access token. Apple processing and any required
review still happen on Apple's schedule. A workflow does not fix an Apple or
Expo service failure; inspect the failed job before retrying.

To start the same workflow directly from the repository root, use:

```sh
pnpm mobile:testflight
```

The command prints the workflow link and waits for the complete result,
returning a nonzero exit code if the workflow fails, is canceled, or waiting
is interrupted. The EAS CLI is a locked dev dependency of `apps/mobile`, so
releases install it from the lockfile and never resolve it on the runner.
Update it with `pnpm add -D --save-exact eas-cli@VERSION` in `apps/mobile`;
the workspace's 14-day release-age rule applies then, not during a release.
`pnpm mobile:testflight:status` reads Apple processing and TestFlight status
using the assigned API key, so you can verify which build reached Apple.
An accepted upload can take several minutes to appear in Apple's build list.

If the build succeeded but uploading failed, copy its EAS build ID from the
workflow and upload it without rebuilding:

```sh
pnpm mobile:testflight:upload --input build_id=YOUR_EAS_BUILD_ID
```

This starts `.eas/workflows/testflight-upload.yml`, which can also be run
from the Expo dashboard. Use the EAS build ID, not the App Store Connect
build ID. Do not upload a build Apple has already accepted; for a new binary,
start the full workflow to get a new build number.

If a submission fails with no logs in its submission record, open its backing
`EAS Submit` run under Workflows and inspect the failed upload job. Apple
`401 NOT_AUTHORIZED` means the stored submission API key is invalid; an Apple
ID session used to configure signing does not authenticate the remote upload.
Run `EXPO_NO_KEYCHAIN=1 pnpm exec eas credentials --platform ios`,
choose production, then App Store Connect to assign a valid API key. Retry
the existing build after fixing credentials. Do not revoke a shared key
without checking its other uses.

## Verify

```sh
pnpm mobile:check
pnpm --filter @hexbot/mobile run export
cargo build --locked --manifest-path backend/hexbot-core/Cargo.toml --bin hexbot
npm ci --prefix backend/pi-runtime --ignore-scripts --no-audit --no-fund
pnpm --filter @hexbot/mobile exec playwright install chromium
pnpm --filter @hexbot/mobile run smoke -- --static
```

The smoke test serves the exported app at iPhone size and uses the real Rust
daemon and pinned Pi. A local OpenAI-compatible streaming fixture replaces only
the model service. It needs no provider credentials and creates disposable daemon
state and workspace directories. Screenshots and `smoke.json` go to a new temp
folder, or `HEXBOT_MOBILE_ARTIFACTS`. CI runs this test and uploads its evidence.

For native testing, start Metro on 8181, then run the smoke without `--static`
and with `--keep`. Read the temporary `native-pairing.json` and use its values:

```sh
maestro test -e DAEMON_ORIGIN=http://127.0.0.1:PORT -e PAIR_CODE=CODE maestro/mobile.yaml
```

On an Android emulator, replace the daemon address's `127.0.0.1` with `10.0.2.2`
and run `adb reverse tcp:8081 tcp:8181` for Metro. The iOS flow supplies the Metro
address through a [launch argument](https://docs.maestro.dev/reference/commands-available/launchapp).
Pairing codes are one-time; mint another on the test daemon for the second
platform. The flow clears only this app's local state, pairs, opens a bot's chat,
sends a native message, waits for its unique reply and opens settings. If the iOS
simulator cannot reset the app, reinstall it and pass `-e RESET_APP=false`.
Stop the smoke process to remove its temporary state.

The connection protocol tests cover Hex Connect grant binding, callback state,
pinned identity checks, device proof and revocation. Production Clerk sign-in
requires an account and registered daemon and is a separate manual check.
